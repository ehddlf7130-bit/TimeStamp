# 순찰 사진 저장 순서 오류 보고서

## 원인

웹 순찰 보관함은 이미 `Shot.time`(사진에 표시된 순찰 시각)으로 정렬하고, 공유할 때도 시간순으로 파일명을 붙이고 있었습니다. 순찰 계획과 목록의 정렬 자체가 원인은 아니었습니다.

문제는 내보내는 사진의 날짜 정보가 목록과 연결되지 않은 점입니다.

- 캔버스에서 생성한 JPEG를 그대로 저장해 EXIF 촬영 날짜가 없었습니다.
- 공유 시 `File`을 만들면서 `lastModified`를 지정하지 않아 각 파일 시각이 공유 당시의 현재 시각으로 생성됐습니다.
- 따라서 파일명과 공유 배열이 시간순이어도, 사진 앱이 날짜 정보나 가져온 순서로 정렬하면 순찰 시각과 다른 순서가 될 수 있었습니다. 다시 찍기·순서를 바꾼 촬영·여러 장 동시 저장에서 파일명 정렬만으로는 이를 해결할 수 없습니다.

위 메타데이터 누락은 코드와 테스트로 확인했습니다. 사용자의 실제 기기 사진 앱에서 발생한 가져오기 순서는 직접 재현하지 않았습니다.

## 수정

- [EXIF 처리](../web/src/core/exif.ts): JPEG에 `DateTime`, `DateTimeOriginal`, `DateTimeDigitized`를 넣고, 각각의 시간대를 `+09:00`으로 기록합니다. 날짜는 사진에 표시된 순찰 시각과 일치합니다.
- [순찰 촬영·복원](../web/src/pages/patrol.ts): 새 사진은 날짜 정보를 넣은 뒤 저장합니다. 기존 보관함 사진은 불러올 때 메모리에서 날짜를 보완하므로 다시 찍지 않고 공유·다운로드할 수 있습니다. 기존 IndexedDB 사진을 일괄 덮어쓰지는 않습니다.
- [공유 파일 생성](../web/src/stamp/export.ts): 순찰 시각을 실제 한국 시각의 Unix 타임스탬프로 변환해 `lastModified`에 전달합니다. 앱의 `Date`는 한국 시각을 UTC 필드에 보관하므로 9시간 보정이 필요합니다.
- 공유 파일 준비는 촬영·복원 시 마쳐, 저장 버튼을 누른 뒤 추가 비동기 작업 없이 공유 시트를 요청합니다.
- JPEG 압축 데이터·색상 정보는 보존합니다. 날짜 헤더만 교체하므로 해상도와 화질을 유지하고, 반복 복원으로 EXIF 헤더가 늘어나지 않습니다. 복원 시 이미지 전체 대신 마커 헤더만 읽습니다.

## 검증

- `npm.cmd test`: 단위 테스트 80개 통과. EXIF 필드·시간대, 자정·연도 경계, 압축 데이터 보존, 반복 적용, 공유 파일 날짜를 검사했습니다.
- `npm.cmd run build`: TypeScript 검사와 프로덕션 빌드 통과.
- `npm.cmd run verify`: 브라우저 통합 검사 99개 통과. 가상 카메라로 순서를 바꿔 촬영·다시 찍기·새로고침 복원·자정 경계·이전 사진 공유와 개별 다운로드를 확인했습니다.
- 실제 다운로드 JPEG를 Windows WIC 디코더로 열어 `DateTimeOriginal=2026:11:11 23:05:00`, `OffsetTimeOriginal=+09:00`, 크기 `3240×3240`을 독립 확인했습니다.

## 적용과 범위

기존 보관함 사진은 수정 버전에서 불러와 다시 저장하면 날짜 정보가 적용됩니다. 이미 휴대폰 사진 앱으로 내보낸 파일의 날짜는 자동으로 바뀌지 않습니다.

사진 앱의 **촬영일 기준 정렬**에 필요한 날짜 정보를 제공합니다. **최근 추가/저장 순서**는 운영체제의 가져오기 처리 결과이므로 웹 앱에서 강제할 수 없습니다. iPhone Safari와 실제 사진 앱의 공유 저장은 실기기 확인이 남아 있습니다.

공개 사이트 반영은 `main`에 푸시한 뒤 GitHub Actions의 테스트·빌드·검증과 Pages 배포가 완료되면 적용됩니다.
